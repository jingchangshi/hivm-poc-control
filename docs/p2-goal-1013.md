## 4. P2-A：独立 Late Pipeline 入口

### 4.1 目标

在现有 RegBase Native Driver 中新增显式 Late 模式。

必须重新读取实际源码：

- `bishengir/tools/bishengir-compile/bishengir-compile.cpp`
- `bishengir/lib/Tools/bishengir-compile/regbase/Driver.cpp`
- `bishengir/lib/Tools/bishengir-compile/regbase/PassPipeline.cpp`
- `bishengir/lib/Tools/bishengir-compile/regbase/BiShengIRCompileMain.cpp`
- 对应 Config、Options、CMake 文件

新增独立、互斥的入口，例如 `--input-ir-stage=late-hivm`，具体拼写需根据当前配置机制确定。

要求：

1. 在 inferLayoutOptimization、inferMixedCV 和普通 RegBase Pipeline 之前分流。
2. 不进入普通 HIR/HFusion 编译路径。
3. 不运行标准 SIMD 的 HIR 优化、VF fusion、UB planning 或 tuning retry。
4. 不使用 `--enable-direct-hivm-lowering` 伪装入口。
5. 不调用 `buildLowerAVEPipelines`。
6. Late 模式只能使用受支持的 Ascend950PR AIV 编译路径。
7. 显式拒绝与 Late 模式不兼容的 SIMT、MixCV、Host、legacy 等选项。
8. 检查 `BISHENGIR_LEGACY_A5_REGBASE`，防止请求被旧驱动截获。
9. 不影响未启用 Late 模式的原有编译请求。

### 4.2 Late 输入验证

在破坏性 IR 转换前建立独立的 Late Input Validator。

检查：

- 输入是真正的 P1 Late HIVM/AVE 阶段，不是 HFusion/Tensor/LLVM 阶段。
- `hacc.target` 在解析时已存在且与 CLI target 匹配。
- module 和 entry core metadata 正确。
- 恰好三个 A/B/C GM 参数，类型及顺序符合契约。
- 输入只使用 P1 已验证的操作集合。
- VF 与 pb32 信息完整。
- GM/UB、DMA 和显式同步符合冻结契约。
- store cache4 符合 D012 已批准的保守 DMA 子集。

Device spec 采用三态规则：

1. **缺失**：根据已验证的目标属性生成完整 spec，且只执行一次 AppendDeviceSpec。
2. **完整且匹配**：验证后复用，跳过覆盖。
3. **部分存在或冲突**：明确拒绝，不允许不完整 spec 进入后续 Pass。

不得把 `UB_SIZE=2031616 bits` 错当成 Kernel 的 `dyn_shared_memory_buf=196608 bytes`。

### 4.3 P2-A 验收

Verifier 必须先冻结入口路由和输入负例。

包括合法 Late 请求、普通 RegBase 请求、缺少目标信息、目标冲突、部分 device spec、错误 core metadata、非法阶段及不兼容编译模式。

## 6. P2-C：真实 A5 Binary 编译

### 6.1 构建身份隔离

P1 v2 使用的 `bishengir-opt` SHA-256 为：

`0761c6e662ee015e30425ee29e0c2314753aa356b21eb4119ff99747327a1977`

这是 P1 的历史编译器身份，不是 P2 新编译产物的预期 SHA。

P2 修改 Driver/Pipeline 后，必须构建新的 `bishengir-compile` 并建立 P2 自己的编译器身份记录。

若 P2 构建会覆盖 P1 固定的可执行文件或 bitcode 路径，应先规划不破坏 P1 快照可复验性的构建/暂存方案，保留原有增量构建能力。

不得修改 D031 的旧 compiler pin 来适应 P2 新构建。

### 6.2 C310 bitcode

确认真实选中的 C310 AIV bitcode。

当前 P1 已证明链接模板 bitcode 中存在：

`l2_cache_mode → zext → shl 60 → descriptor → MOV.UB.TO.OUT.ALIGN.V2.DV`

P2 必须进一步证明新的 Kernel 编译链实际消费了正确的 bitcode。

检查：

- bitcode 绝对路径与 SHA-256。
- O0/O2 选择。
- `bishengir-compile` 的实际 executable path。
- `../lib` 中实际选择的模板。
- 第四个 i32 Store libcall 参数与模板 ABI 一致。
- cache4 在最终 Kernel 所使用的链接/优化链中未被替换为 cache0。
- 不存在使用旧 bitcode、缓存对象或回退模板的情况。

Late 模式下找不到要求的 C310 bitcode，必须直接失败。

不要只根据一个独立模板具有正确的 cache4 dataflow 就宣称最终 Kernel 正确。

### 6.3 LLVM 与 Kernel ABI

通过真实编译输出检查：

1. 设备入口对应三个 GM 指针参数。
2. Kernel symbol 与 FunctionInfo 所需信息一致。
3. AIV core type 和 Ascend950PR target 正确。
4. 不产生额外设备入口参数。
5. blockIdx 获取和 GM 偏移符合 Golden。
6. pb32 Lowering 结果保持 b32。
7. DMA 的 load/store 地址和范围符合预期。
8. set_flag/wait_flag 及终止屏障没有被错误删除或重排。
9. dynamic UB=196608 作为启动契约保留，不误写为设备容量。
10. 无未合法化的 HIVM/HIVMAVE 或 unrealized cast。
11. 真实 `ConvertHIVMToLLVM` 恰好运行一次。

最终必须生成一个新的真实 A5 AIV Kernel Binary，记录可复现命令、退出码、SHA-256、符号及目标信息。

文件存在或编译器 exit 0 不足以宣布 P2 成功。

## 7. P2-D：独立验证和 Challenger 审查

Verifier 的正式验收要与 Implementor 实现独立。

测试分为：

**A. 入口及 Pipeline**

- 正确 Late 分流。
- 普通 RegBase 路径不变。
- 错误 target、错误阶段、错误 core、错误 device spec 拒绝。
- 禁止 Pass 未执行。
- 必需 Pass 顺序正确。
- LLVM Lowering 仅一次。

**B. 语义反例**

- cache4→cache0 能被值级别断言发现。
- 删除 cache carrier 能被发现。
- 非法 store cache 和 D012 不支持的 layout 明确拒绝。
- 删除 pb32 能被发现。
- 删除入口末尾 PIPE_ALL 能被发现。
- 将 PIPE_ALL 移入 VF 或错误控制流位置不能获得假 PASS。
- 改变 UB byte offsets、DMA payload 或 GM block offset 不能获得假 PASS。
- 缺少或使用错误的 C310 bitcode 明确失败。

测试必须证明它因预期的语义断言失败，而不是仅仅由于输入 SHA 不匹配或 MLIR 解析出错而失败。

**C. 编译器与旧路径回归**

将 D012 已验证的关键正反例转化为仓库内可维护的 MLIR 回归测试。

检查默认 cache0、第四个 C310 参数、非 C310 路径保留旧 ABI。

旧 RegBase SIMD 路径至少执行受 Driver 改动影响的代表性编译回归。

未受影响的完整 E0/Triton E2E 不必机械重复，但凡受到当前 Driver、LLVM 或 Runtime 变更影响的验收均需针对性复验。

**D. 二进制真实性**

- 新 Binary 来自本轮 P2 编译。
- Binary 与输入、编译器及 bitcode 的身份关系可追溯。
- 删除或替换输出后重编译能够产生真实新产物。
- 旧 Binary 不能冒充新 P2 输出。

Challenger 必须独立审查最终 Git diff、实际执行日志和关键负例。

裁决必须为 APPROVE、REVISE 或 BLOCK。

不得把仅有源码推断的项目标记为已执行 PASS。
